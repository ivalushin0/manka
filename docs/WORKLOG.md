  не меняется на повторном apply.
- `engine_sig` включал `ls -lR`: вывод зависит от TZ, после ребута первый apply перезапускал движок без изменений

## 2026-11-16 — Telegram «еле коннектится»: прокси работал под root, без обхода
- Причина: tg-ws-proxy запускался от uid 0, а root исключён из nfqws (SYS_UIDS). Под uid 2000 (обход есть) тот же
  бинарь с теми же аргументами сразу поднимает `DC2 → pool hit via 149.154.167.220` и CF-домены, сессии живут
  26–37 с по 0.3–1 МБ. Под root DPI режет TLS: `kws*.web.telegram.org` и CF-домены у root — 000 за 8 с, у uid 2000 —
  404 за 0.4 с; в дебаг-логе прокси `DC2 IP in cooldown → skipping direct WS` и таймауты всех CF-доменов.
  Ухудшилось это не от правок 13.11: просто раньше прокси перезапускался каждые ~30 мин и после перезапуска
  успевал поставить свежие соединения, а теперь перезапусков нет и стало видно постоянное поведение.
- Исправление: `tgws-run.sh` запускает прокси через `su 2000 -G 3003`; бинарь копируется в `/data/local/tmp/manka`
  (`/data/adb` для uid 2000 закрыт). `--dc-ip` больше не вырезаются, прокси не перезапускается по пробам: разбор
  адресов только рвал соединения, а прокси сам уходит в Cloudflare по `--ip-fail-cooldown`. `tgws_sum` учитывает
  и бинарь, чтобы обновление модуля перезапускало прокси. `tgws-probe` теперь запускается от того же uid: сначала
  CF-домены, потом TCP прямого адреса (nc — слабая проверка: TCP отвечает, пока TLS/WS режется).
- Проверено на телефоне. Wi-Fi TrapHata: прокси uid 2000, 23 живых соединения на 149.154.167.220, probe ok.
  Мобильная сеть: профиль mobile, обход 200/404, probe ok, прокси при переключении сети **не перезапускался**.
  Возврат на Wi-Fi: снова прямой фронт, probe ok.

### Не повторять
- Не запускать tg-ws-proxy от root: root в SYS_UIDS, обход его не трогает, и DPI режет TLS к Telegram-фронту и к
  CF-доменам — Telegram «еле коннектится», при этом `nc -z` и TCP-проверки показывают «всё ок».
- Не судить о доступности Telegram-фронта по `nc -z`: TCP отвечает и там, где TLS/WS уже режется.
- В CI нельзя отдавать `testReleaseUnitTest` из кэша Gradle: экспорт стратегий (`build/strategies`) и прокси-конфигов

## 2026-11-20 — Telegram перестал работать совсем: прокси держал сокеты старой сети
- Симптом: Telegram «Соединение…», не грузит ни текст, ни картинки; в модуле при этом всё зелёное
  (`tgws_running=1`, `tgws-probe` — ok).
- Причина 1: процесс tg-ws-proxy жил с 16.11 и пережил десяток смен сети. На Wi-Fi у него было 27 соединений,
  привязанных к адресу **мобильной** сети (10.37.69.110 при текущем 192.168.3.63). Пул переиспользовал эти мёртвые
  сокеты, поэтому не работало ничего. `tgws-probe` врал «ok», потому что поднимает отдельный экземпляр с чистого
  листа.
- Причина 2 (следствие): Telegram сам выключил прокси — в `mainconfig.xml` `proxy_enabled=false`; приложение ушло
  в прямой обход-DPI и показывало «Соединение…».
- Исправление: прокси перезапускается при смене сети (`tgws_restart` в `cmd_net_apply` и в `cmd_start`, если ключ
  сети изменился) — соединения там и так рвутся; плюс самовосстановление в `tgws_check`: если у прокси есть
  IPv4-сокеты, но ни один не на текущем адресе маршрута (смена IP в мобильной сети может пройти без смены маршрута),
  он перезапускается. Проба по-прежнему ничего не перезапускает.
- Проверено на телефоне: Wi-Fi (pid 24521, сокеты на 192.168.3.63) → мобильная (pid 26320, 10.37.69.110, CF) →
  Wi-Fi (pid 27588, снова прямой фронт); Telegram подключался каждый раз, плановый `tgws-check` на правильной сети
  не перезапускает. Прокси в Telegram включён обратно (правка `mainconfig.xml` при остановленном приложении).

### Не повторять
- Не оставлять tg-ws-proxy жить через смену сети: его пул держит сокеты, привязанные к интерфейсу, и после
  переключения они мертвы, а Telegram показывает «Соединение…» при зелёном статусе модуля.
- Telegram может сам выключить прокси после долгой неработоспособности (`proxy_enabled=false` в
  `shared_prefs/mainconfig.xml`) — тогда не поможет ни один перезапуск модуля, надо включать прокси в приложении.

## 2026-11-22 — Telegram «очень хреново»: DPI режет SNI фронта, прокси уходил в публичный Cloudflare
- Версии компонентов на телефоне уже последние: zapret v72.13, zapret2 v1.0.7, byedpi v0.17.3,
  tg-ws-proxy-rs v2.7.2 (вышел 20.11 20:47 МСК — уже попал в сборку 0.1.0-51), dnsproxy v0.86.0, xray v26.11.9.
- Диагностика с телефона (uid 2000, через обход): TCP до фронта 149.154.167.220 открывается, но TLS с SNI
  `kws2.web.telegram.org`, `kws4`, `kws5`, `www.google.com` — таймаут, а с SNI `sprinthost.ru` **на том же IP** —
  302 за 0.4 с. Значит блок по SNI. Без подмены SNI прокси падал в публичные CF-домены, где медиа получает
  «HTTP/2 POST 404», и картинки не грузились вообще.
- Дебаг-лог с `--fronting-domain sprinthost.ru`: `DC2 → WS connected via 149.154.167.220 (fronted SNI
  sprinthost.ru)`, медиа-сессии по 1–4 МБ (`DC2m ↓4.1MB`, `DC203 ↓731KB`, `DC5 ↓574KB`).
- Ещё две наши настройки мешали: `--ws-connect-timeout 3` (дефолт 10) обрывал рабочий handshake, а лестница
  апстримов доходила до прямого TCP к DC, его таймаут сажал IP в кулдаун (`DC2m TCP ... cooldown 60s` →
  `IP in cooldown → skipping direct WS`) и выключал рабочий WS на минуту.
- Изменения: в `NetLists`/`net/manka-net.json` (версия 2) добавлен `tgws_fronting` = `sprinthost.ru`; `Applier`
  передаёт `--fronting-domain`, таймаут WS 8 с, `--pinned-upstream ws,cfproxy` и `--pinned-media-upstream ws,cfproxy`.
- Проверено на телефоне: с новыми аргументами прокси держит 8 прямых соединений к 149.154.167.220, Telegram
  подключается (20 сокетов к 127.0.0.1:1443), медиа идёт.
- Позже в тот же день фронт стали резать выборочно: из 23 попыток WS прошли 3, остальные таймаут (даже с
  подменой SNI), публичные CF-домены отвечают reset/404. Поэтому в README добавлена инструкция со своим
  Cloudflare Worker (`docs/cf-worker.js`, режим `--cf-worker-domain`): Worker открывает TCP к DC, фронт и
  публичные прокси не нужны. Лестница апстримов теперь `ws,cfworker,cfproxy,mtproto` — worker и MTProto-прокси
  остаются рабочими, выброшен только прямой TCP к DC (его таймаут сажал IP в кулдаун).

### Не повторять
- Не проверять доступность Telegram-фронта без SNI: DPI режет именно по имени, тот же IP с другим SNI отвечает.
- Не ставить таймаут WS 3 с: DPI задерживает handshake, прокси уходит на медленный CF и медиа отваливается.
- Не позволять лестнице апстримов пробовать прямой TCP к DC: его таймаут сажает IP в кулдаун и выключает рабочий WS.
